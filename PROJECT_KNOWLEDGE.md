## 1. Overview

SkillSync is a three-service recruiting platform:

- **`client/`** — React 18 + Vite + TypeScript SPA. Job search/apply for candidates, an admin dashboard (jobs, applicants, ATS scores, analytics), Google Sign-In auth.
- **`server/`** — Express monolith (ESM, `type: module`). MongoDB/Mongoose. Owns auth, jobs, applications, resume parsing/ATS scoring, Google Calendar OAuth + booking, and a small "phone-agent" facing API surface used by the phone-agent service.
- **`phone-agent/`** — Standalone Express + `ws` service that bridges Twilio Media Streams (phone audio) to the Gemini Live API, so a candidate can have a live voice interview with an AI agent. Calls back into `server/` over HTTP using a shared bearer token for context, calendar availability, and booking.
- **Root (`/`)** — npm workspace glue (`package.json` scripts run all three via `concurrently`), a single root `.env` shared by `server` and `phone-agent`, `docker-compose.yml`/`docker-compose.mongo.yml`, and `scripts/smoke.mjs`.

Relationship: client talks only to `server` (`/api/*`). `server` talks to MongoDB, AWS S3, Google Gemini (text), Google Calendar, and (for outbound calling) `phone-agent`. `phone-agent` talks to Twilio, Google Gemini Live, and back to `server` (`SKILLSYNC_API_BASE_URL`) using `SKILLSYNC_SERVICE_TOKEN`. There is no message queue or shared cache — all cross-service communication is synchronous HTTP.

## 2. Data models

All six Mongoose models live in `server/src/models/`. Fields below are exactly what's declared — nothing inferred.

### 2.1 `Job` (`models/Job.js`)
- `recruiterId: ObjectId ref User, default null` — **added on `fix/local` (Stage 4).** The admin who owns this job's interview scheduling; resolved to a specific Google Calendar by `phoneAgentCalendarController.resolveRecruiterForApplication` (§3.4). Not `required` at the schema level (see below for why), but always set going forward by `JobService.createJob` (§3.7).
- `title: String, required`
- `location: String, required`
- `workType: String, enum ['Full-time','Part-time','Contract','Internship'], default 'Full-time'`
- `status: String, enum ['draft','active','closed'], default 'draft'`
- `summary: String, required if !description`
- `keyResponsibilities: String, default ''`
- `requiredSkills: String, required if !requirements`
- `preferredSkills: String, default ''`
- `aboutCompany: String, default ''`
- `compensation: String, default ''`
- `description: String, default ''`
- `requirements: String, default ''`
- `createdAt: Date, default now`
- `keywords: [String], default []`
- `searchableTitle: String, default = title.toLowerCase()`
- Indexes: text index over `title/location/description/requirements/keywords` (weighted), plus single-field indexes on `title`, `searchableTitle`, `location`, `status`, `createdAt`.

**Missing fields (verified absent):** no `department` field (referenced defensively in `jobServiceInternal.js`/`ATSScoreService` as `job.department || ''` but never declared or set on the schema — always empty/undefined in practice), no `updatedAt`/timestamps option, no soft-delete flag. (The "no owning admin/recruiter field" gap from the original audit is now fixed — see `recruiterId` above.)

`recruiterId` is deliberately **not** `required: true` at the schema level: making it required would mean `Job.findByIdAndUpdate(..., { runValidators: true })` (used by `JobService.updateJob`) starts failing full-document validation on any legacy job that couldn't be backfilled (§3.7's backfill script leaves `recruiterId: null` if no admin has a connected calendar and `GOOGLE_CALENDAR_ADMIN_USER_ID` isn't set) — a surprising breaking change for an unrelated edit. A `null` recruiterId is instead an explicitly handled case in the calendar-resolution logic (§3.4), not a validation error.

### 2.2 `Application` (`models/Application.js`)
- `userId: ObjectId ref User, required`
- `jobId: ObjectId ref Job, required`
- `candidateInfo: { name: String, email: String }`
- `resume: { fileUrl, s3Key, fileName, fileType, fileSize: Number, uploadedAt: Date }` (all default `null`)
- `atsScore: { score: Number(0-100, default null), breakdown: Mixed, matchSummary: String, analyzedAt: Date, status: enum ['pending','processing','completed','failed'] default 'pending', error: String }`

**Missing fields:** no owning-admin/recruiter reference (mirrors Job — nothing ties an application to a specific recruiter), no `updatedAt`/timestamps, no interview-scheduling fields (no `interviewDate`/`interviewEventId` — interview state for the modern Application-based flow lives only in Google Calendar itself, see §3.4/§8).

### 2.3 `Candidate` — **removed on `fix/local` (Stage 5)**
This section originally documented a separate, older/parallel model from `Application`, populated only by an admin **bulk resume upload** path — no fields, indexes, or scoring shared with `Application`. It has been retired: per an explicit product decision ("candidates always self-apply through the portal with their own resume"), `Application` is now the sole source of truth for candidates.

Before deleting anything, the `Candidate` collection was checked and confirmed **empty (0 documents)** in this repo's database — no data migration was needed or performed.

Removed entirely: `server/src/models/Candidate.js`, `server/src/controllers/candidateController.js`, `server/src/routes/candidateRoutes.js` (and its `/api/candidates/*` mount in `app.js`), `server/src/services/CandidateService.js` (the LLM resume-extraction service used only by the bulk-upload path). Investigation before removal found **no live client code ever called `/api/candidates/*`** (grepped `client/src` for any reference — zero hits), so nothing user-facing needed to be found-and-removed on the client side; the "admin UI tied to bulk resume upload" this stage asked to search for did not exist.

Also removed as part of the same cleanup (found while tracing every remaining `Candidate` reference): the **candidate-search feature** — `searchService.js`'s `Candidate`-backed functions, `searchController.js`'s `searchCandidates`/`unifiedSearch`/`getCandidateSuggestions`, and the corresponding `searchRoutes.js` routes (`/candidates`, `/unified`, `/suggestions/candidates`) — plus the client-side `SearchPage.tsx`, `CandidateSearch.tsx`, `UnifiedSearch.tsx`, `SearchResults.tsx`. This was already **dead code before removal**: `SearchPage` was never imported by `App.tsx` or reachable from any route (same pattern as the `AdminDashboard.tsx`/`pages/Dashboard.tsx` dead code noted elsewhere in this doc), so nothing was reachable from the live app either way. `searchJobsWithFilters`/`getJobSuggestions` (job search, `/api/search/jobs`, `/api/search/suggestions/jobs`) were kept untouched — they don't use `Candidate` and weren't part of this cleanup's scope, even though (separately, pre-existing, not addressed here) no live client code calls them either — `JobsList.tsx`'s job search/filtering is done entirely client-side against the already-fetched `/api/jobs` list, not via `/api/search/jobs`.

`server/src/services/applicationServiceInternal.js`'s dashboard-stats functions (`countInterviewsScheduledForUser`, `getAdminCandidateCounts`) used `Candidate.countDocuments({interviewScheduled:true})` for the `interviewsScheduled` metric shown on both the candidate and admin dashboards. **There is no equivalent signal on `Application`** — interview booking (§3.4) writes only to Google Calendar, with no write-back to `Application` or `CallSession` indicating "an interview was booked." Both functions now return `0` for this metric, with a comment explaining why, rather than querying a deleted model or silently dropping the field from the API response. This is a real, currently-unfilled gap — flagged in §7/§8 — not a full fix.

**Missing fields:** no `userId`/link back to a `User` account — a `Candidate` row is not connected to any authenticated user, only to a free-text `name`/`email` pulled from the resume by the LLM. No link to `Application` either. `email` has no `unique` constraint, so duplicate `Candidate` rows for the same real person are possible.

## 3. Workflows

### 3.1 Candidate call intake (Twilio → phone-agent → Gemini)

Two ways a call happens; both converge on the same WebSocket handler.

**A. Admin-triggered outbound call** (from the SkillSync dashboard):
1. Client calls `POST /api/phone/call { applicationId }` → `server/src/routes/phoneRoutes.js:7`, guarded by `authenticate` + `requireAdmin`.
2. `phoneController.callCandidate` (`server/src/controllers/phoneController.js:14`): loads `Application` → loads `User` → validates `user.phoneNumber` is set → `fetch(`${PHONE_AGENT_BASE_URL}/twilio/call`, { to, applicationId })`.
3. `phone-agent`'s `POST /twilio/call` (`phone-agent/src/twilio.routes.js:47`): resolves its own public URL, calls `Twilio.calls.create({ from: twilioPhoneNumber, to, url: <voiceUrl>?applicationId=... })`. Returns `{ sid }`.
4. Back in `phoneController.js:66-81`: best-effort creates a `CallSession` row (`callSid`, `applicationId`, `userId`, `jobId`, `status:'initiated'`) — wrapped in try/catch so a telemetry failure doesn't fail the call.
5. Twilio calls back `POST /twilio/voice` on phone-agent (`twilio.routes.js:83`) — **signature-verified** via `Twilio.validateRequest` against the exact reconstructed webhook URL (`getWebhookUrlForSignature`); returns TwiML `<Connect><Stream url=".../twilio/stream?applicationId=...">` — `applicationId` is carried forward from the `/voice` query string.
6. Twilio opens the WSS connection to `/twilio/stream`; `phone-agent/src/server.js:36-45` only upgrades exactly that path.

**B. Genuinely inbound call** (candidate dials the Twilio number directly): same `/twilio/voice` → `/twilio/stream` path, but with **no `applicationId` query param** (nothing set it). See §8 for what this means for context resolution.

**WebSocket handler** (`phone-agent/src/twilio.mediaStream.js:handleMediaStream`):
- Reads `applicationId` off the WS URL query string if present (`applicationIdFromUrl`, line 20-27).
- On Twilio's `start` event (line 248-256): captures `streamSid`/`callSid`, calls `ensureGeminiStarted(callSid)`.
- `ensureGeminiStarted` (line 185-230): if `applicationIdFromUrl` is set, uses it directly. Otherwise, tries `GET /api/phone-agent/calls/:callSid/application-context` (`skillsyncFetch`) to resolve an `applicationId` from a previously-written `CallSession` row matching that `callSid` — **this lookup can only succeed if some other code path already wrote a `CallSession` with that `callSid` and a non-null `applicationId` before the call started**, which (per §2.5) nothing in the current codebase does other than path A above (and path A already has `applicationIdFromUrl` set, so it never needs this fallback). Failure here is caught and logged as a warning; the call proceeds with `appId = null`.
- Calls `createLiveSession({ applicationId: appId, onmessage, onerror, onclose })` (`gemini.liveSession.js`, §3.2).
- Buffers inbound Twilio `media` frames (`pendingMedia`) until the Gemini session is ready, then drains them and fires the greeting (`tryTriggerGreeting`, line 142-165) — a synthetic first user turn instructing Gemini to greet the candidate, only once `geminiReady && streamSid` are both set.
- Audio in: Twilio `media` event → base64 μ-law → `mulawToPcm16k` (`audio.pipeline.js`) → `session.sendRealtimeInput({ audio: { data, mimeType: 'audio/pcm;rate=16000' } })`.
- Audio out: Gemini `onmessage` → `serverContent.modelTurn.parts[].inlineData` (audio/pcm, rate from mimeType, `parseRateFromMime` fallback 24000) → `PcmToMulaw8kStream` (stateful resampler+encoder, rebuilt if the input rate changes) → chunked into 160-byte (20ms) Twilio `media` frames → `ws.send`. If `serverContent.interrupted` is set (barge-in), sends a Twilio `clear` event to flush buffered audio.
- Teardown: any of Twilio `stop`/`close`/`error`, or Gemini `onerror`/`onclose`, funnels into `closeAll(reason)` (line 44-58), which closes the Gemini session and the Twilio WS, guarded by a `closed` flag so it only runs once.

### 3.2 Gemini Live session lifecycle (`phone-agent/src/gemini.liveSession.js`)

`createLiveSession(callbacks)`:
1. Instantiates `new GoogleGenAI({ apiKey: process.env.GEMINI_API_KEY })` (`@google/genai` SDK — the **Live**-capable client, distinct from server's `@google/generative-ai`).
2. Logs whether `SKILLSYNC_SERVICE_TOKEN` is configured (warns if not — tool calls will fail later).
3. `ai.live.connect({ model: 'gemini-3.1-flash-live-preview', config: {...}, callbacks: {...} })`:
   - `responseModalities: [Modality.AUDIO]`
   - `systemInstruction`: a hardcoded system prompt (lines 8-38ish) — interviewer persona, told to greet by first name from private context, keep responses short/conversational, never reveal private context unprompted, a **call-length note** (added on `fix/local`, Stage 3: call is ~6-7 minutes by design, pace accordingly, and if a "system note" says time is almost up, wrap up within the next turn rather than waiting for the candidate), and a hard rule that **all scheduling is Asia/Kolkata (IST)** and must use tool-provided `voiceLabel`/`startIso` verbatim, never guessing or converting timezone.
   - `inputAudioTranscription: {}` / `outputAudioTranscription: {}` (added on `fix/local`, Stage 3) — enables Gemini Live's built-in speech-to-text for both sides of the call; delivered incrementally as `serverContent.inputTranscription.text` / `serverContent.outputTranscription.text` chunks on ordinary `onmessage` events (not a separate channel), consumed in `twilio.mediaStream.js` (§4) to build a rough transcript.
   - `toolConfig.functionCallingConfig`: `mode: AUTO`, `allowedFunctionNames` = the 4 declared tool names.
   - `tools: [{ functionDeclarations: toolDeclarations }]` — 4 tools, see §3.3.
   - **`sessionResumption` is not set. `contextWindowCompression` is not set.** (Verified: these keys are absent from the `config` object passed to `ai.live.connect`.) This is intentional as of Stage 3 — see the call-timeout paragraph below instead of resumption.
4. Session callbacks:
   - `onopen`: logs, forwards to caller's `onopen`.
   - `onmessage`: first checks for function calls via `extractFunctionCalls` (handles three possible shapes Gemini Live may use — `toolCall.functionCalls`, `serverContent.toolCall.functionCalls`, `serverContent.modelTurn.parts[].functionCall`, plus a legacy `toolCalls[].functionCalls` array). If any are present, dispatches them (§3.3) and **returns without calling the caller's `onmessage`** for that message (i.e. tool-call messages never reach `twilio.mediaStream.js`'s audio/transcript handler). Otherwise forwards the raw message to `callbacks.onmessage` (which is `handleGeminiMessage` in `twilio.mediaStream.js`, i.e. audio playback + transcript capture).
   - `onerror`/`onclose`: logs and forwards to caller's callbacks (which call `closeAll`, tearing down the whole call — **no reconnect/retry logic anywhere in this path**).
5. After connecting, if `callbacks.applicationId` was provided, immediately sends a synthetic user turn (`sendClientContent`) telling the model the `applicationId` and that it may call `getApplicationContext` with no arguments — this is how the tools avoid needing the ID passed on every call.
6. Returns the live `session` object (which `twilio.mediaStream.js` holds in a per-connection closure variable and calls `.close()` on during teardown).

**Call-length handling (added on `fix/local`, Stage 3 — `phone-agent/src/twilio.mediaStream.js`):** rather than implementing session resumption around Gemini Live's documented ~10 minute connection ceiling, calls are deliberately kept short. Two `setTimeout`s are armed right after `geminiReady` flips true (i.e. once the Live session is actually up): at `WRAP_UP_AFTER_MS` (5 min) a synthetic user turn (`WRAP_UP_NUDGE_TEXT`) is sent telling the model time is almost up and to start wrapping up; at `HARD_CLOSE_AFTER_MS` (7 min) `closeAll('call duration limit reached')` fires unconditionally, tearing the call down regardless of where the conversation is — both comfortably inside the ~10 minute ceiling. Both timers are pushed onto a per-connection `callTimers` array and cleared in `closeAll` (so a call that ends earlier for any other reason doesn't leave stray timers running). This is a fixed-budget mitigation, not a general solution — a call that needs longer than ~7 minutes (e.g. a chatty candidate) is cut off rather than extended.

### 3.3 Gemini agent tools (`toolDeclarations` + dispatch in `gemini.liveSession.js:onmessage`)

All four tools are dispatched inside the same `onmessage` handler; each result (or error) is collected into a `responses` array and sent back in one `session.sendToolResponse({ functionResponses: responses })` call (line 227-231). All four are simple pass-throughs to `skillsyncFetch` (`phone-agent/src/skillsyncClient.js`) — an authenticated fetch to `server` with `Authorization: Bearer ${SKILLSYNC_SERVICE_TOKEN}`.

1. **`getCurrentTimeIst`** — no args. `GET /api/phone-agent/time` → `phoneAgentCalendarController.nowIst` (`server/src/controllers/phoneAgentCalendarController.js:39`): returns current Luxon `DateTime` in `Asia/Kolkata`, plus a spoken-friendly `voiceLabel`. No DB access, cannot fail except on a server-down error.

2. **`getApplicationContext`** — optional `applicationId` (falls back to `callbacks.applicationId` from call setup). If neither is present, **throws locally in phone-agent** before any network call (`gemini.liveSession.js:174-177`) — "Missing applicationId". Otherwise `GET /api/phone-agent/applications/:applicationId/context` → `phoneAgentController.getApplicationContext` (`server/src/controllers/phoneAgentController.js:55`): loads `Application` → `User`/`Job`, returns candidate name/email, job title, job requirements. `resumeSummary`/`interviewScript` are always `null` (not implemented). 404s if the application doesn't exist.

3. **`getInterviewSlots`** — optional `week: 'auto'|'next'`; `applicationId` optional (falls back to `callbacks.applicationId`, same pattern as tool 2). **Changed on `fix/local` (Stage 4):** previously this handler never sent `applicationId` to the server at all (a real gap — availability was being resolved without any notion of which job it was for); it now throws locally (same "Missing applicationId" pattern as the other tools) if neither `args.applicationId` nor call metadata has one, then calls `GET /api/phone-agent/calendar/availability?week=&applicationId=` → `phoneAgentCalendarController.availability` → `resolveRecruiterForApplication` (§3.4) → `GoogleCalendarService.getAvailableSlots`. Returns a list of 60-minute slots (Mon–Fri, 10:00–18:00 IST) with `startIso`/`endIso`/`voiceLabel`, computed against a live Google Calendar `freebusy.query` on the resolved recruiter's calendar.

4. **`bookInterviewSlot`** — requires `slotStartIso` (also accepts `startIso`/`slotStartISO`/`startISO` aliases from the model); `applicationId` optional (same fallback). Missing `applicationId` throws locally before the network call (line 192-195), same pattern as tool 2. `POST /api/phone-agent/calendar/schedule` → `phoneAgentCalendarController.schedule` (line 66) → loads `Application`/`Job`/`User` for title/description/attendee → `GoogleCalendarService.scheduleInterview` → `calendar.events.insert` with `sendUpdates: 'all'` (emails the candidate an invite). Returns `eventId`, `htmlLink`, ISO times, and a `voiceConfirmation` string.

**Failure handling for all four**: caught in a per-call `try/catch` inside the `for (const call of functionCalls)` loop (line 217-225) — the error's `.message` is put into `response: { error: msg }` and sent back to Gemini as the tool result (not thrown to the process). The system prompt explicitly instructs the model to "read it once to the candidate in simple words and try once more — do not invent times" on a tool error string. If `session.sendToolResponse` itself throws, that's caught separately and only logged (line 229-231) — the model would then be left waiting for a response that never arrives, with no explicit timeout/recovery coded.

### 3.4 Calendar availability & booking, and admin-calendar resolution

Two parallel entry points hit the same `server/src/services/GoogleCalendarService.js` functions:

- **Admin, in-app** (`server/src/routes/calendarRoutes.js`, `authenticate + requireAdmin`): `GET /api/calendar/availability` and `POST /api/calendar/schedule` → `calendarController.js` → still uses **`adminUserId: String(req.userId)`** — i.e. the calendar of whichever admin is currently logged in and calling the API. **Deliberately left unchanged in Stage 4**: verified via grep that no client code calls either endpoint (`client/src` only ever calls `GET /api/calendar/auth-url`, §3.5) — these are a self-service "admin looks at/books time on their own calendar" pair, a different use case from the phone-agent's per-job routing below, and Stage 4's ask was scoped to the phone-agent path (`/api/phone-agent/calendar/availability` and "the actual booking step" of that same flow).
- **Phone-agent** (`server/src/routes/phoneAgentRoutes.js`, `requirePhoneAgent` shared-token guard): `GET /api/phone-agent/calendar/availability`, `POST /api/phone-agent/calendar/schedule` → `phoneAgentCalendarController.js`. **Rewired on `fix/local` (Stage 4):** both routes now require `applicationId` (query param for `availability`, body field for `schedule` — the latter already required it) and resolve the calendar via `resolveRecruiterForApplication(applicationId)`: `Application.findById` → `Job.findById(application.jobId)` → `Job.recruiterId` → that `User`'s `googleCalendarRefreshToken`. The old `resolveCalendarAdminUserId()` — "first admin found with a connected calendar, arbitrary if more than one qualifies" — has been removed from this controller. Fallback order, in code: (1) the job's `recruiterId`, if that user has a connected calendar; (2) `GOOGLE_CALENDAR_ADMIN_USER_ID`, only if explicitly configured by the operator (an intentional opt-in default, not a DB-order-dependent guess), logged via `logger.warn` when used; (3) a clean `ApiError(400, ...)` with a candidate-appropriate message — different wording depending on whether the job has no `recruiterId` at all vs. has one but that recruiter hasn't connected a calendar. All five branches (missing applicationId, nonexistent application, resolves-and-proceeds, no-recruiter-and-no-fallback, recruiter-without-calendar-and-no-fallback) were exercised live against the dev database and behaved as designed, including full cleanup of the throwaway test `Job`/`Application` documents used for the two fallback-path tests.

`GoogleCalendarService.getAuthorizedCalendarClient(adminUserId)` (line 58-69): loads that `User`, requires `googleCalendarRefreshToken` to be set, constructs an `OAuth2Client`, `setCredentials({ refresh_token })`, builds a `calendar` client. **No proactive validation that the refresh token still works** — that's still true, and still by design (that's what the Stage 3 health-check script is for, run on a schedule, not on every request). What changed on `fix/local`: when the token *is* invalid/revoked and `freebusy.query`/`events.insert` throws Google's raw `invalid_grant` (or similar OAuth failure) at request time, that error is no longer allowed to leak straight through to the caller. `GoogleCalendarService.js` exports `isGoogleAuthError(error)` — checks `error.message`/`error.response.data.error` for `invalid_grant`/`invalid_token`/`invalid_client` — and both `phoneAgentCalendarController.js` (`availability`, `schedule`) and `calendarController.js` (`availability`, `schedule`) now wrap their `getAvailableSlots`/`scheduleInterview` calls in a try/catch that converts a detected auth failure into a clean `ApiError(400, ...)` with audience-appropriate wording: the phone-agent path reuses the exact same candidate-friendly message `resolveRecruiterForApplication` already used for "recruiter has no token at all" (from the candidate's perspective, "token present but broken" and "no token" mean the same thing — scheduling isn't available right now); the admin-direct path gets an actionable message telling the admin to reconnect via the dashboard. Any other error (e.g. the existing `409` double-booking conflict from §3.4) is re-thrown unchanged — `isGoogleAuthError` only matches actual OAuth-failure signatures, verified against the real `invalid_grant` error this was built to catch (see §9 for the incident that surfaced this).

`getAvailableSlots({ adminUserId, week })` (line 95-162): computes a Mon–Fri IST business-hours window (`getWorkWeekWindow`, handles weekend → next Monday, and `week:'next'` → the following Monday), calls `calendar.freebusy.query` for `primary` calendar busy blocks in that window, then generates all 60-minute slots in `[10:00,18:00)` IST and filters out any that overlap a busy block (`overlaps`, simple interval-overlap check). **Does not re-check for concurrent bookings between two calls to this function** — it's a live read of freebusy each time, so it reflects Google's calendar state at call time, but see next paragraph for the booking side.

`scheduleInterview({ adminUserId, slotStartIso, ... })` (`server/src/services/GoogleCalendarService.js:164-`, updated on `fix/local`): parses `slotStartIso` with Luxon, computes a 1-hour end time, then **re-runs `calendar.freebusy.query` for exactly that `[startIst, endIst)` window immediately before `calendar.events.insert`** — if that window shows as busy (i.e. something else booked it since the candidate/admin last saw availability), the call throws `ApiError(409, 'That slot was just booked. Please choose another time.')` instead of double-booking. This narrows — but does not fully close — the TOCTOU window: there is still a small gap between the re-check read and the `events.insert` write themselves (no distributed lock or idempotency key), so two requests racing within that narrow window could in principle still both pass the check and both insert. A full fix would need a lock/reservation record; this is the "simplest version" fix, re-verifying immediately before the write rather than relying on a possibly-stale earlier `getAvailableSlots` read. Both the admin-triggered path (`calendarController.schedule`) and the phone-agent path (`phoneAgentCalendarController.schedule` → `bookInterviewSlot` tool, §3.3) go through this same function, so both get the re-check. See §9 verified issue #2 (updated status).

Ownership: **as of `fix/local` (Stage 4), `Job.recruiterId` (§2.1) makes per-job calendar routing real** — the phone-agent path above resolves each job to its own assigned admin's calendar rather than one shared organization-wide calendar. This is still one connected calendar per admin (`User.googleCalendarRefreshToken`, §2.4 — unchanged), so a single admin can be `recruiterId` for many jobs and all of those still land on that one calendar; there's no per-job *calendar*, only per-job *recruiter assignment*. The admin-facing `calendarController` routes above are unaffected by this — they were never job-scoped to begin with.

**Backfill (Stage 4):** `server/scripts/backfillJobRecruiterId.mjs` (`npm run backfill:job-recruiter`) sets `recruiterId` on every pre-existing `Job` that has none, choosing the *same* admin the old `resolveCalendarAdminUserId()` fallback would have picked (env var, else first admin with a non-empty token) — this makes the previously-implicit owner explicit without moving any already-scheduled interview to a different calendar. Run once against this repo's dev database: backfilled all 11 existing jobs. Worth flagging: it assigned them to the admin the Stage 3 health-check script (§3.4 above) found has an **invalid** (`invalid_grant`) token — not a bug in the backfill (it faithfully reproduces the old fallback's "does a token string exist" check, not "does it still work"), but real state worth fixing operationally: either that admin reconnects (§3.5's Connect/Reconnect button), or an admin manually updates `recruiterId` on the affected jobs to a different admin who has a working connection.

**Token health check (added on `fix/local`, Stage 3):** `server/scripts/checkCalendarTokens.mjs` (`npm run check:calendar-tokens`, from repo root or `server/`) finds every `User` with `role:'admin'` and a non-empty `googleCalendarRefreshToken`, and for each one calls `OAuth2Client.getAccessToken()` (a real refresh-token→access-token exchange against Google — the same exchange `getAuthorizedCalendarClient` does implicitly on first use) to force any `invalid_grant`/revoked-token error to surface immediately rather than silently at booking time. Prints one line per admin (`OK`/`INVALID` + reason) and exits `1` if any are invalid, `0` otherwise — meant to run on a schedule (cron/CI), not from application request paths. It does not update the database or notify anyone automatically (that's the "reconnect via the dashboard" step, §3.5) — it's a detection tool, not a remediation one. Verified working against this repo's live dev database: correctly reported one connected admin's token invalid (`invalid_grant`) and one valid.

### 3.5 Google OAuth connect/reconnect (Calendar)

Endpoints (`server/src/routes/calendarRoutes.js`):
- `GET /api/calendar/auth-url` (`authenticate + requireAdmin`) → `calendarController.authUrl` (line 41-45): signs a short-lived (`10m`) JWT `state` binding `{ t: 'gcal', userId: req.userId }` (`signState`, line 20-22), then `GoogleCalendarService.getCalendarAuthUrl(state)` → `oauth.generateAuthUrl({ access_type: 'offline', prompt: 'consent', scope: ['.../auth/calendar'], state })`. Returns `{ url }` to the (admin) caller, which must open it in a browser themselves.

(This corrects one of the seeded known-issues — see §9.)
- `GET /api/calendar/oauth/callback` (public, no auth — Google redirects here directly) → `calendarController.oauthCallback` (line 47-90): handles Google-side error params (renders an HTML error page), requires `code` and `state`, `verifyState(state)` (JWT verify, checks `t==='gcal'`), then `GoogleCalendarService.exchangeCalendarCodeAndStore({ userId, code })` (line 35-56): `oauth.getToken(code)`, throws 400 if no `refresh_token` came back (this happens if the user previously granted consent and Google doesn't re-issue a refresh token — mitigated here by always requesting `prompt: 'consent'` on the auth-URL step, which forces a refresh token every time), then `User.updateOne({ _id: userId }, { $set: { googleCalendarRefreshToken, googleCalendarConnectedAt: new Date() } })`. Renders a plain "Calendar connected" HTML page on success.
- **Admin UI added on `fix/local` (Stage 3):** `client/src/components/admin-dashboard/calendar-connect-card.tsx` (`CalendarConnectCard`) is rendered on the admin dashboard (`admin-dashboard/dashboard-page.tsx`, admin-only route). Its "Connect"/"Reconnect" button calls `GET /api/calendar/auth-url` and opens the returned URL with `window.open(url, '_blank', 'noopener,noreferrer')` — the OAuth consent flow happens in a new tab so the admin's SPA session isn't disrupted; there's a "Refresh status" button to re-check `/auth/me` afterward (no postMessage/polling handshake with the popup — deliberately kept lightweight). - **Adjacent fix:** while wiring this card, `GET /api/auth/me` (`server/src/routes/authRoutes.js`) was found to return the full `User` document minus only `password` — meaning `googleCalendarRefreshToken` (a live OAuth secret) was being sent to the browser on every "who am I" check. Fixed to `.select('-password -googleCalendarRefreshToken')`. The card only ever needed `googleCalendarConnectedAt` (a timestamp, not sensitive), so nothing about the new feature depended on the leaked field.

### 3.6 Admin authentication and authorization

- **Sign-in is Google-only.** `POST /api/auth/google` (`googleAuthController.postGoogleAuth`): verifies a Google ID token (`OAuth2Client.verifyIdToken`, audience = `GOOGLE_CLIENT_ID`) — not an OAuth code flow, this is the One Tap/GIS credential flow. Looks up `User` by `googleId`; if not found, tries to link a legacy password-only account by matching `email` (and stamps `googleId`/`profilePhotoUrl` onto it). If a user is resolved, issues an access token (`TokenService.generateAccessToken`) and returns it + a formatted user. If not, issues a short-lived (`15m`) **onboarding** JWT (`type:'onboarding'`) and returns `{ needsOnboarding: true, tempToken }`.
- `POST /api/auth/onboarding` (`postOnboarding`): requires the onboarding token, requires `role` to be exactly `'admin'` or `'user'` **as supplied by the client** (`googleAuthController.js:119-121` — the comment on the function even says "role is user-supplied (acceptable for tiny private deploys only)"), requires a `profile` object, creates the `User`. This means **any first-time Google sign-in can self-select `role: 'admin'`** — there is no invite code, allow-list, or existing-admin approval step.
- `client/src/components/auth/AuthSplitScreen.tsx` (renamed/replaced `LoginForm.tsx`/`RegisterForm.tsx` on `fix/local`, shared by `AuthPage`/`RegisterPage` via a `mode` prop) confirms this: it renders only `<GoogleSignInSection />`, no username/password fields — despite `User.password` existing in the schema with full validation, **no route anywhere issues or checks a password-based login** (grep of all `routes/*.js` found only `/api/auth/google`, `/onboarding`, `/logout`, `/me` — no `/login` or `/register`). The password field/validator appears to be dead code for the current auth flow (or vestigial from an earlier version).
- Session model: stateless JWT access tokens (`type:'access'`, default 15m expiry) verified per-request by `middleware/auth.js:authenticate` — extracts Bearer token, checks `TokenBlacklist` (§2.6), `jwt.verify`, checks `type==='access'`, loads the `User` fresh from DB every request (no caching), sets `req.user`/`req.userId`. `requireAdmin` just checks `req.user.role === 'admin'` (must run after `authenticate`).
- **No refresh-token flow is wired up**: `TokenService.generateRefreshToken`/`generateTokenPair`/`refreshAccessToken` all exist and are fully implemented, but no route calls any of them — access tokens simply expire after 15 minutes with no renewal path found in the client (`client/src/context/AuthContext.tsx` was not found to call any refresh endpoint — not exhaustively traced line-by-line, flagged as unverified in §8).
- Logout (`POST /api/auth/logout`, `authenticate`) blacklists the current access token (`TokenService.blacklistToken`) with `reason:'logout'`; TTL-indexed so it self-expires from Mongo at the token's own `exp`.
- Protected vs public, by route file: `jobRoutes` — reads public, writes `authenticate+requireAdmin` (including `DELETE /:id`, §3.7); `applicationRoutes` — all `authenticate`, admin-only subset `requireAdmin`; `profileRoutes` — all `authenticate` (`router.use(authenticate)`); `dashboardRoutes`/`analyticsRoutes` — all `authenticate`; `phoneRoutes` — `authenticate+requireAdmin`; `calendarRoutes` — admin-only except the public OAuth callback; `phoneAgentRoutes` — entirely gated by `requirePhoneAgent` (shared token, not a user JWT at all) via `router.use(requirePhoneAgent)`; `searchRoutes` — fully public, job-search only as of Stage 5 (§2.3).

### 3.7 Job / application creation & status-change workflows

**Job creation** (admin): `client/src/components/CreateJob.tsx` (not exhaustively traced line-by-line) → `POST /api/jobs` (`authenticate+requireAdmin`, `validateJobCreation` middleware) → `jobController.createJob` → `JobService.createJob(jobData, recruiterId, req)` (`server/src/services/JobService.js`): requires `title/location/summary/requiredSkills`, defaults `status` to `JOB_STATUS.ACTIVE` (**not** `draft`, despite the schema's own default being `'draft'` — the service layer overrides it), inserts via `Job.create`. **Changed on `fix/local` (Stage 4):** `jobController.createJob` now passes `req.userId` (the authenticated admin — guaranteed non-null by the route's `authenticate` middleware) through as `recruiterId`, so every newly-created job is auto-assigned to whichever admin created it; no client change needed since this isn't client-supplied. Update (`PUT /api/jobs/:id`) is a straightforward `findByIdAndUpdate`, admin-only — `recruiterId` can be changed by an admin editing a job's fields like any other field (no dedicated "reassign recruiter" endpoint; not asked for).

**Delete (`DELETE /api/jobs/:id`, admin-only, added on `fix/local` — Stage 5):** already worked with no status restriction (deletable in `draft`/`active`/`closed` alike — nothing in `JobService.deleteJob` ever checked `status`). What changed is what it does: **hard delete, cascading** — explicit product decision, not soft-delete despite the `Application.withdraw` soft-delete precedent from Stage 2 (the user overrode the suggested soft-delete default: "complete deletion... leaving no trace/record for admin and user"). `JobService.deleteJob` now: loads every `Application` for that `jobId`, best-effort deletes each one's S3 resume (`S3Service.deleteFile`, wrapped in its own try/catch — one failed S3 delete is logged and skipped, not fatal to the rest, verified live: this env has no AWS config, so every S3 delete attempt failed with a real error, and the job+applications were still fully deleted), then `Application.deleteMany({jobId})`, then `Job.findByIdAndDelete`. `CallSession` rows referencing the job are deliberately left alone — they're pure backend telemetry with no user-facing view, so "no trace for admin and user" doesn't reach them, and every place that reads `CallSession.jobId` already tolerates a null lookup gracefully. Verified live against the dev database with disposable throwaway `Job`+`Application` documents (one with a fake `s3Key` to force the S3-failure path): job and both applications correctly gone afterward, and calling delete again on the same (now-gone) id correctly 404s rather than erroring differently.

Client: `JobDetails.tsx` gained a `Delete` button next to the existing admin-only `Edit` button, gated the same way (`isAdmin`), using the same `AlertDialog` confirm-before-destructive-action pattern already used for `Withdraw Application` in the same file — "This action cannot be undone... will permanently delete '{title}' and every application submitted for it, including uploaded resumes." On success it navigates back to `/jobs` (the job page would otherwise 404) and calls `triggerDashboardRefresh()`.

**Candidate applies**: `client/src/components/ApplyModal.tsx` — client-side validates file size (<5MB) and mimetype, then raw `fetch('/api/applications/job/:jobId/apply', { method:'POST', body: FormData, headers: { Authorization } })` (note: this component uses a hand-rolled `fetch`, not the shared `apiClient` in `lib/api.ts`). Server: `multer` (`upload.single('resume')`, memory storage, 5MB limit, PDF/DOC/DOCX only) → `applicationController.applyForJob` → `ApplicationService.createApplication` (`server/src/services/ApplicationService.js:13-102`):
  - Validates job exists and `status === 'active'` (rejects applying to draft/closed jobs).
  - Checks for an existing `Application` for this `{userId,jobId}` — if it was previously `withdrawn`, **reactivates it in place** (resets `status`/`appliedAt`, clears `withdrawnAt`) rather than creating a new row (respects the unique `{userId,jobId}` index); if it exists and isn't withdrawn, rejects with 400 ("already applied").
  - Uploads resume to S3 (`S3Service.uploadResume` — sanitizes filename, validates extension again server-side, keys as `resumes/user-{id}-{timestamp}.{ext}`), then creates the `Application` doc with `status:'applied'`, `atsScore.status:'pending'`.
  - Controller then fires `ApplicationService.triggerATSAnalysis` via `setImmediate(...).catch(logger.error)` — **fire-and-forget**: the HTTP response returns immediately with `atsAnalysisStatus: 'pending'`; ATS scoring happens after the response, and if it throws, the only trace is a `logger.error` call — no retry, no user-facing notification beyond polling `GET /api/applications/:applicationId/ats-status` (§3.7 error handling below).

**ATS scoring pipeline** (triggered above, or manually via `POST /api/applications/:applicationId/retry-analysis`, admin-only): `ResumeAnalysisService.analyze` (`server/src/services/ResumeAnalysisService.js`): loads `Application`+`Job`, requires a resume `s3Key`, sets `atsScore.status='processing'`, `ResumeParserService.parseResumeFromS3` (downloads from S3, `pdf-parse` for PDF / `mammoth` for DOCX, `.doc` is explicitly rejected as unsupported), then `ATSScoreService.generateATSScore` (`server/src/services/ATSScoreService.js`): builds a scoring prompt, calls `generateGeminiText` (server's `@google/generative-ai` wrapper) with **3 retries and linear backoff** (`1000*attempt` ms) on any failure (line 41-93), parses a rigid `SKILLS:/EXPERIENCE:/EDUCATION:/KEYWORDS:/MATCH_SUMMARY:` text format out of the response (falls back to a single-number regex if the structured parse fails), computes a weighted total (`skills .35, experience .30, education .15, keywords .20`), and writes `atsScore.{score,breakdown,matchSummary,analyzedAt,status:'completed'}` back onto the `Application`. **Bug found and fixed on `fix/local`**: the parsing regexes in `parseDetailedScoreFromResponse` and `stripMarkdownFences` were written with double-escaped backslashes (`/SKILLS:\\s*(\\d+)/i` instead of `/SKILLS:\s*(\d+)/i`) — in a JS *regex literal* (as opposed to a string), `\\` means "match a literal backslash character," not "whitespace/digit escape passed through." So these regexes were structurally looking for literal backslash characters in Gemini's plain-text response, which never appear — every real response failed the structured parse, fell through to the single-number fallback regex (`/\\d+/`, same bug), which also never matched, so `generateATSScore` always threw `"No numerical score found in AI response"` after all 3 retries. This meant **ATS scoring had likely never worked against a real Gemini response** — it only ever "succeeded" if some other, earlier failure (e.g. a quota error) short-circuited before parsing ran, so the bug was invisible until quota stopped being the blocker. (The same double-escape mistake is explicitly called out and correctly avoided elsewhere in this codebase — `server/src/utils/querySanitizer.js`'s `sanitizeObjectId` has a comment reading *"do NOT use `/\\d/` here; in regex literals that matches a literal `\d`."* — so this exact footgun was already known to at least one contributor, just not caught here.) Fixed by removing the extra backslash from all six affected regex literals; verified with plain, markdown-fenced, and deliberately-malformed sample responses run directly through `ATSScoreService`'s methods (no live Gemini call) — all three parse paths (structured, fence-stripped, single-number fallback) now produce correct results. On any unrecoverable error (including exhausting all 3 Gemini retries), the outer `try/catch` in `ResumeAnalysisService.analyze` sets `atsScore.status='failed'`, `atsScore.error=<message>`, and re-throws (caught by the fire-and-forget wrapper in the controller, logged only).

**Withdraw**: `DELETE /api/applications/job/:jobId/withdraw` → `ApplicationService.withdrawApplication`: requires an existing, non-withdrawn application. **As of `fix/local`, this now soft-deletes**: sets `status: 'withdrawn'` and `withdrawnAt: new Date()` on the existing document and saves it, rather than hard-deleting the row or removing the resume from S3. The S3 resume is deliberately left in place (not deleted) because `createApplication`'s "reactivate a withdrawn application" branch (above) re-activates the *same* document and its existing `resume` fields without re-uploading — that reactivation path only works if the S3 object it points to still exists. Because the document now persists, `ApplicationService.getApplicationStatus` was also changed to report `applied: false` for a `status:'withdrawn'` application (previously any existing row meant `applied:true`) — this keeps `JobDetails.tsx`'s "Apply Now" button showing for a candidate who withdrew, which is what actually makes the reactivation branch reachable end-to-end rather than just reachable-in-theory. Prior to this fix the row was hard-deleted (`findByIdAndDelete`) and the S3 file was deleted too, which left the reactivation branch in `createApplication` as dead code — see §9 (was open question #5 in the original audit, now resolved).

**Status change (admin, e.g. Shortlist/Reject/Hire)**: `client/src/components/ApplicantsList.tsx` (`handleStatusChange`, confirmed via grep) → raw `fetch('/api/applications/:applicationId/status', { method:'PATCH', body: { status } })`, wired from `ApplicationStatusDropdown.tsx`'s `onStatusChange`. Server: `PATCH /api/applications/:applicationId/status` (`authenticate+requireAdmin`) → `applicationController.updateApplicationStatus` (`server/src/controllers/applicationController.js:169-201`). **Fixed on `fix/local`**: this handler references `Application.findById(applicationId)` (line 188), which previously threw `ReferenceError: Application is not defined` because the model wasn't imported in this file — `import Application from '../models/Application.js';` has since been added (`applicationController.js:1`). See §9.

**Legacy admin bulk-upload path — removed on `fix/local` (Stage 5).** This subsection used to document a second, non-integrated "schedule an interview" mechanism built on the `Candidate` model (`POST /api/candidates/job/:id/upload`, `POST /api/candidates/:id/schedule`, with no Google Calendar interaction at all). It has been deleted in full — see §2.3.

### 3.8 Error handling / logging summary (cross-workflow)

- **server**: consistent `ApiError` + `catchAsync` + central error middleware pattern (`app.js:148-163`) for routes built on the newer `ApplicationService`/`JobService`/`GoogleCalendarService` stack — thrown `ApiError`s carry a status code and message straight to the client as JSON. Non-`ApiError` exceptions (bugs, driver errors, the `Application`-not-imported bug above) fall through to a generic 500 with `err.message` exposed directly to the client — i.e. **internal error messages/stack info can leak to API responses** for unexpected errors (mitigated only by the messages themselves usually being non-sensitive Node error text).
- Older controllers (some of `phoneController.js`, `googleAuthController.js` — `candidateController.js` was another example until it was removed in Stage 5, §2.3) use manual `try/catch` + `ApiResponse.error`/raw `res.status().json()` instead of `catchAsync`/`ApiError` — two coexisting error-handling conventions in the same codebase.
- **ATS scoring**: the only workflow with real retry logic (3x, linear backoff) — `ATSScoreService.generateATSScore`. Everything else is single-attempt.
- **Fire-and-forget paths** (no retry, error only logged, never surfaced to the triggering user in real time): ATS analysis after apply (`setImmediate` in `applicationController.applyForJob`); best-effort `CallSession` creation in `phoneController.callCandidate` (explicit empty `catch`); Gemini tool-call failures inside a live call (returned to the model as an error string, not thrown — by design, so the AI can narrate it, per the system prompt).
- **phone-agent**: no retry anywhere. `skillsyncFetch` throws on any non-2xx or network failure; every call site catches it and either (a) logs + treats as absent context (`ensureGeminiStarted`'s CallSession lookup), or (b) surfaces the error string back to Gemini as a tool response (all 4 tools). A Twilio signature-validation failure returns 401 immediately, no logging of the payload. WebSocket/Gemini errors always tear down the entire call (`closeAll`) — there is no partial-failure recovery, e.g. losing SkillSync connectivity mid-call kills the whole interview rather than degrading gracefully.
- **Logging infrastructure differs per service**: `server` uses `winston`, writing structured JSON to `server/logs/{combined,error}.log` (5MB rotation ×5 files) plus colorized console in non-production (`utils/logger.js`). `phone-agent` uses a hand-rolled `console.log/warn/error` wrapper (`phone-agent/src/logger.js`) with **no file transport, no rotation, no structured/JSON format** — in production this only goes to stdout (captured by whatever process manager/Docker log driver is in front of it, not by anything in-repo). There is no shared request/call-correlation ID threading server logs to phone-agent logs for the same phone call — correlating them today would require manually matching timestamps or `callSid`/`applicationId` strings across two separate log streams.

**Module-level / shared state found** (flagged as-is, not necessarily risky given what it holds):

Whatever transcript exists at teardown (built from `inputAudioTranscription`/`outputAudioTranscription` chunks) is now persisted to `CallSession.transcript` via `POST /calls/:callSid/end`, regardless of which path triggered `closeAll` (§2.5, §4 table above) — this was not true at the time of the original audit.

## 5. External integrations & their constraints

- **Twilio** (Voice + Media Streams): outbound calls via `twilioClient.calls.create` (`phone-agent/src/twilio.routes.js`); inbound webhook (`/twilio/voice`) is signature-verified using `Twilio.validateRequest` against the exact reconstructed public URL. `POST /twilio/call` is guarded by `requireSkillsyncAuth` (`phone-agent/src/requireSkillsyncAuth.js`, added on `fix/local`) — the same shared-bearer-token pattern as `server`'s `requirePhoneAgent`, checked with a timing-safe compare (`phone-agent/src/timingSafe.js`). `server/src/controllers/phoneController.js` now sends `Authorization: Bearer ${SKILLSYNC_SERVICE_TOKEN}` when it calls `/twilio/call`, and refuses to call out at all if `SKILLSYNC_SERVICE_TOKEN` isn't configured server-side. Media Streams audio is μ-law 8kHz, 20ms (160-byte) frames — the codec math in `audio.pipeline.js` is built around exactly that framing. Twilio-side call/stream duration limits were **not verified in this codebase** (external to what static code can confirm) — flagged in §8.
- **Gemini Live API** (`@google/genai`, model `gemini-3.1-flash-live-preview`, hardcoded): real-time bidirectional audio session. As covered in §4, this repo does not configure session resumption or context compression, and Google's documented session/connection-duration limits for Live sessions were not (and cannot be) verified from source code alone — flagged as an external-behavior assumption in §8.
- **Gemini text API** (`@google/generative-ai`, server-side, models configurable via `GEMINI_MODEL`/`GEMINI_ATS_MODEL`): used for ATS scoring (the legacy candidate-extraction use of this API was removed with `CandidateService.js`, Stage 5, §2.3). No explicit rate-limit handling beyond `ATSScoreService`'s generic 3-retry/backoff (not specifically tuned for 429/rate-limit errors vs. any other failure — every error type gets the same retry treatment).
- **Google Calendar API** (`googleapis`, OAuth2 offline access + refresh token stored per-`User`): `freebusy.query` (read) and `events.insert` (write, `sendUpdates:'all'` so Calendar itself emails the invite — no separate email-sending code in this repo). Google Calendar API has its own quota/rate limits (per-project and per-user) that are not specifically handled here (a quota error would just propagate as a generic thrown error, same as any other Calendar API failure — see §3.4).

  **Accepted limitation — 7-day refresh-token expiry (recorded on `fix/local`, Stage 5.2, no code change):** while this Google Cloud project is in testing mode (unpublished / not verified by Google), every OAuth refresh token it issues expires after 7 days regardless of use, which is why an admin's calendar connection periodically goes invalid even with `prompt:'consent'` correctly forcing a fresh refresh token on each reconnect (§3.5). **This is accepted as-is for now** — the fix is Google app verification/production publishing, which is a deliberate, separate decision to make later, not a code change. What *is* in place to make the 7-day cycle bearable: the `prompt:'consent'` fix (ensures reconnecting always yields a usable new refresh token, §3.5's issue #4 area) and the Stage 3 token health-check script (`server/scripts/checkCalendarTokens.mjs`, §3.4) so an expired token is caught by a scheduled check instead of by a candidate mid-call. **Do not "fix" this by chasing Google app verification/publishing work unless explicitly asked** — it wasn't asked for here and is an external, account-level process, not a code task.
- **AWS S3**: resume storage. Pre-signed URLs default to 1-hour expiry (`S3_CONFIG.PRESIGNED_URL_EXPIRY`, `constants.js:28`). No lifecycle/retention policy logic in-repo (would be an S3 bucket-level config, not application code).
- **ngrok** (dev-only): `publicBaseUrl.js` can resolve the phone-agent's public URL by querying a local ngrok agent's `/api/tunnels` API — only used when `PUBLIC_BASE_URL` isn't set directly; irrelevant in a production deployment with a real public URL.

## 9. Verified issues

Each of the seven issues supplied was independently re-checked against the current code (not taken at face value). Findings below reference exact file:line locations from this audit.

1. **No `sessionResumption`/`contextWindowCompression` on the Gemini Live session; no reconnect/resumption on drop.** — **CONFIRMED, and still true by design after `fix/local`.** `phone-agent/src/gemini.liveSession.js`: the `config` object passed to `ai.live.connect` still contains no `sessionResumption` or `contextWindowCompression` keys. `onerror`/`onclose` still forward straight to `closeAll` in `twilio.mediaStream.js`, tearing down the whole call with no retry/backoff/reconnect. What changed on `fix/local` (Stage 3) is the *consequence*, not this fact: calls are now deliberately bounded to ~7 minutes (wrap-up nudge at 5 min, hard `closeAll` at 7 min — §3.2, §4), comfortably inside Gemini Live's documented ~10 minute ceiling, so hitting that ceiling — and needing resumption at all — should no longer happen in normal operation. A call that runs long for other reasons (e.g. slow candidate) is still cut off at 7 minutes rather than resumed.

2. **No conflict check/lock at interview-booking time; double-booking possible.** — **CONFIRMED at time of audit; partially fixed on `fix/local`.** `GoogleCalendarService.scheduleInterview` used to go straight to `calendar.events.insert` with no `freebusy.query` immediately before the write. It now re-runs `freebusy.query` for the exact `[start,end)` window right before `events.insert` and throws `409` if that window is busy (§3.4). This closes the main gap (a stale `getAvailableSlots` read from earlier in the call/conversation no longer causes a silent double-book) but is not a full fix: there's still no lock/reservation between the re-check read and the insert write, so two requests racing within that narrow window could theoretically both pass. A true fix would need a short-lived reservation record or a distributed lock — out of scope for this pass.

3. **Calendar admin resolved via env var / "first admin with a token" global fallback; `Job`/`Application` don't store an owning admin.** — **CONFIRMED at time of audit; fixed on `fix/local` (Stage 4).** The nondeterministic `User.findOne({ role:'admin', googleCalendarRefreshToken: {...} })` "first match" fallback has been removed from `phoneAgentCalendarController.js` entirely. `Job.recruiterId` now exists (§2.1) and is what resolves the calendar (§3.4); `GOOGLE_CALENDAR_ADMIN_USER_ID` is retained only as an explicit, operator-opt-in fallback (not a DB-order-dependent guess) for jobs whose recruiter is unassigned or hasn't connected a calendar. Existing jobs were backfilled (`server/scripts/backfillJobRecruiterId.mjs`, §3.4).

4. **Google OAuth auth-URL generation may be missing `response_type: 'code'`.** — **NOT CONFIRMED / CORRECTED.** `GoogleCalendarService.getCalendarAuthUrl` (`server/src/services/GoogleCalendarService.js:25-33`) does not explicitly pass `response_type`, but the underlying `google-auth-library` `OAuth2Client.generateAuthUrl` defaults it: `server/node_modules/google-auth-library/build/src/auth/oauth2client.js:125` — `opts.response_type = opts.response_type || 'code';`. The generated URL does include `response_type=code`. This issue does not reproduce against the installed library version; no code change is needed here unless the library version changes that default.

12. **`triggerDashboardRefresh` was silently broken everywhere it was called, and even fixed it wouldn't have forced a fresh fetch** — user-reported: after the Stage 5.3 job-delete button succeeded server-side, the UI showed a "Failed to delete job" toast anyway, and the jobs list stayed stale until a manual page reload. Root cause, found by tracing the exact error text to its only source (`client/src/components/JobDetails.tsx`'s `handleDeleteJob` catch block): `client/src/context/DashboardContext.tsx`'s `DashboardProvider` only ever provided `{ refreshTrigger, triggerRefresh }` on the context, but `ApplyModal.tsx` and `JobDetails.tsx` (both `handleWithdraw`, pre-existing, and the new `handleDeleteJob`) destructure `triggerDashboardRefresh` — a name the `DashboardContextType` type declares as `triggerDashboardRefresh?: () => void; // Legacy support` but that was never actually wired up on the Provider. Calling it called `undefined()`, throwing a `TypeError` that landed in each handler's `catch` block — so a successful delete (or withdraw, or apply) always showed a false failure toast, and because the exception happened before any refresh signal was sent, `refreshTrigger` never actually incremented via these paths either. Second, deeper issue found while fixing the first: even with `triggerDashboardRefresh`/`triggerRefresh` correctly wired, bumping `refreshTrigger` alone wasn't enough — `useApi`'s effect re-runs on a `refetchTrigger` change, but it calls `apiClient.get(endpoint, { cacheTime, skipCache })` without `skipCache:true`, so it kept serving `client/src/lib/api.ts`'s module-level `responseCache` if the cache entry was still within its TTL (3-5 minutes), regardless of the trigger changing — explaining "I need to refresh my page again and again."
    **Status: FIXED** — `DashboardContext.tsx`'s Provider now aliases `triggerDashboardRefresh: triggerRefresh` (so every existing call site starts working without being touched individually), and `triggerRefresh` now also calls `apiClient.clearCache()` before bumping the counter, so the next `useApi` fetch triggered by any mutation (apply, withdraw, delete, edit) actually hits the network instead of replaying stale cached data. This was a pre-existing bug — not something introduced by the Stage 5.3 delete feature, which only inherited/exposed it by copying the same (already-broken) pattern used in the neighboring `handleWithdraw`.

13. **ATS scoring could never actually parse a real Gemini response — double-escaped regex literals in `ATSScoreService.js`** — user-reported via server logs (application submitted successfully, but `ATS analysis failed: Failed to generate ATS score: No numerical score found in AI response` after 3 retries, once an unrelated Gemini quota issue was separately resolved). Root cause: `parseDetailedScoreFromResponse` and `stripMarkdownFences` used `\\s`/`\\d` inside regex *literals* (`/SKILLS:\\s*(\\d+)/i` etc.) — which matches a literal backslash character, not whitespace/digits — so the structured-format parse always failed, and the single-number fallback regex (`/\\d+/`) had the identical bug and also never matched, so `generateATSScore` always threw after exhausting retries. Full details and fix verification in §3.7.
    **Status: FIXED** — replaced all six affected regex literals with correctly-escaped `\s`/`\d`. Verified directly against `ATSScoreService`'s methods (no live Gemini call, to avoid quota) with a plain structured response, a markdown-fenced one, and a deliberately unstructured one — all three now parse/score correctly.
